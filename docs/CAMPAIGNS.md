# Campaigns (multi-thread coordinator)

Status: P0 to P6 implemented, P7 partly in: the optional headless runner is the server-side campaign driver of `flint serve --agent-run` (see "A server-driven campaign" below and `docs/MOBILE.md`, "What P3 does"), while pane-bound parallelism on the desktop, the 12-worktree disk cost and an orphan sweep that deletes remain open (backend improvements for conflicts, plan edits, verification trust, estimate, campaign diff and notifications are in, see "Backend improvements"); a simplified board and an explicit "New campaign" start are in (see "Simplified UX" under Status, and "Using campaigns"). The feature is called Campaigns in the UI and `campaign` in code, because "project" already means a folder in Flint.

## Goal

One conversation acts as a coordinator. It splits a prompt into at most 12 tasks with dependencies. Each task runs as its own top-level Cowork session on its own `flint/...` worktree branch, in parallel up to a bounded limit. Context and decisions pass between threads. The coordinator verifies each result, merges in dependency order into an integration branch, and hands one proposal to the user's checkout for approval. Local only; no cloud sessions.

Non-goals: replacing subagents or the Cowork team (those stay for in-run delegation), auto-merging into the user's checkout, widening permissions, and extracting the Cowork run loop in the MVP.

## Data model

Stored under `<data>/campaigns/<campaign_id>/`, written with `atomic_file.rs`, with an append-only `events.jsonl` via `event_log.rs`.

- `campaign.json`: id, title, coordinator session, source root, base branch and sha, integration branch and worktree, mode ceiling, model, limits (max parallel, max tasks, token budget, per-task tokens and steps, wall clock), status, process epoch, and the task list.
- Each task: id, title, brief, acceptance criteria, declared paths, `dependsOn`, session id, branch, worktree path, base sha, status, attempt, verdict, tokens used, handoff path, merged sha, fingerprint.
- `decisions.md`: append-only, written by the coordinator only.
- `tasks/<id>/handoff.md`: a task's final summary, changed files and open questions.

Project status: `draft`, `planned`, `approved`, `running` (or `paused`), `reviewing`, `merging`, `done`, `failed`, `cancelled`. A running record from an earlier process epoch reads as `interrupted`.

Task status: `pending`, `blocked`, `queued`, `running`, `awaiting_input`, `awaiting_approval`, `completed`, `verifying`, `verified`, `merged`, plus `failed`, `cancelled`, `interrupted`, `conflict`. `completed` is only a worker claim; `verified` requires a verification PASS and a missing verdict is BLOCKED, never PASS. Retries are capped at 2.

A session gets an optional `campaign: {id, taskId, role}` pointer. The backend record is the source of truth for status.

## Coordinator flow

1. The coordinator session calls `campaign_plan` with the task list. The backend validates limits, cycles and path overlap.
2. The user approves a plan card (always-ask, allow once) that shows task count, paths, mode, budget and parallelism.
3. The backend ensures the integration worktree and writes `campaign.json`.
4. The scheduler starts every task whose dependencies are `merged`, up to the parallel limit. For each: create a session, ensure a worktree based on the integration branch, register with the mailbox, seed the first turn with the brief, acceptance criteria, a `decisions.md` snapshot and upstream handoffs (fenced as untrusted data), open a pane so the run can start.
5. When a task's run ends, the renderer writes `handoff.md`, commits pending changes, records the fingerprint and notifies the coordinator.
6. The coordinator collects results and runs verification per task, with one repair round on FAIL or PARTIAL.
7. Verified tasks merge into the integration branch in topological order. A conflict aborts the merge, marks the task `conflict`, and spawns a resolver task or parks it for the user.
8. When everything is merged, run the final build and test gate on the integration worktree, then create a single proposal to the user's checkout through the existing proposal path. The user approves the apply.

## Context passing

No transcripts cross threads. Briefs go in seed turns, not in mail, to stay inside mailbox rate limits. Mid-run steering uses the mailbox or `campaign_steer`. A task writes only its own handoff; only the coordinator appends decisions.

## Limits, cancellation, recovery

- At most 12 tasks. Max parallel threads is a user setting (Settings, Campaigns). Default 4, allowed range 1 to 6, matching the split-pane limit (`SPLIT_DEFAULT_MAX_PANES=4`, hard max 6). It is read when the scheduler starts a task, so changing it applies to running campaigns without a restart. Free panes still cap the effective value.
- Token budget per task and per project; warn at 80 percent, stop spawning at 100 percent. Wall-clock cap and step cap per task.
- Cancel a task with `abortRun`. Cancel the project by aborting running tasks and marking queued ones cancelled. Worktrees are discarded only on an explicit user action.
- On startup, reconcile: records from another process epoch become `interrupted`. Resume re-ensures worktrees, fingerprints changes and re-queues. Unfinished work is never treated as clean.

## Security

A task's mode is the minimum of the project ceiling and the coordinator's mode; `bypass` is never inherited. Tasks use managed-worktree access. Plan approval does not pre-approve tool calls. Mailbox content, handoffs and briefs are untrusted and fenced. Campaign tools are never given to tasks or subagents. Org policy and hooks apply per session unchanged. Declared paths are advisory for scheduling; the real boundary is the worktree plus the apply-time proposal.

Implemented (P4: verify, merge, gate, propose):

- Backend `campaign_integration.rs`, commands `agent_campaign_verify_prepare`, `_verify_finish`, `_merge_task`, `_integrate`, `_gate_plan`, `_finalize`, `_refresh`, `_orphans`.
- **Verify.** `verify_prepare` re-derives the task worktree from Git, builds the verifier request with `verification::build_request` (task spec and acceptance, the committed diff, the output of the detected build or test command, and the handoff as a fenced worker claim; worker reasoning is not passed) and moves the task to `verifying`. The renderer runs that request with the campaign's model (`RunnerHost.askVerifier`, a utility-agent call with no tools, audited) and hands the reply to `verify_finish`, which uses `parse_report`. This is the answer to open question 12: the Rust `ModelInvoker` is not reachable from the renderer, so the renderer owns the model call and the backend owns the framing and the verdict. PASS makes the task `verified`. FAIL or PARTIAL gets one repair round (`RepairBudget`, 1): the task is queued again in its own session, its `detail` carries the findings and its seed turn fences them as data (done through the seed turn rather than mailbox mail, to stay out of mailbox rate limits and to reuse the pane and worktree it already has); a second FAIL or PARTIAL is `failed`. BLOCKED, an unreachable model, an empty reply or a reply with no VERDICT line stays `completed` with verdict BLOCKED and never merges. The runner verifies automatically when a task settles `completed`; `campaign_verify` retries.
- **Merge.** `merge_task` and `integrate` merge `verified` tasks into the integration branch with `worktree::merge` in topological order. Before anything is read or merged the recorded worktree path, branch and base are matched against Git: the path must be a worktree of the source repository listed on that branch, under Flint's worktrees folder, on a `flint/` or `jan/cowork/` branch, in the state it was recorded in, and the base commit must be in the branch history. A task depends only on merged work. The merge is tested with `merge-tree` first, so a conflict moves no ref and aborts nothing half-done: the task becomes `conflict` with `detail` naming the files and `campaign_merge` returns them. A merged task records `mergedSha` and the runner starts the tasks that were waiting on it. Conflicts are parked for the coordinator (steer the task to rebase on the integration branch, or skip it with `campaign_merge skip=[...]`); spawning a resolver task is not built.
- **Gate and proposal.** When every task is merged or cancelled (at least one merged) the campaign moves to `reviewing` and the coordinator is told. `campaign_merge finalize=true` asks the user (always-ask, shows the gate command), then `finalize` moves to `merging`, runs the gate command on the integration worktree and, when it passes, stores ONE proposal against the campaign's base commit through the ordinary proposal store (`proposal::create`); nothing is written to the user's checkout. A failing gate returns to `reviewing` with the output kept in `campaign.gate`. Gate command source: `[campaign] gate = "..."` in `.jan/agent/agent.toml` (there was no existing build or test key), else the repository's own `package.json` `test` then `build` script (run with yarn, pnpm or npm by lockfile), else `cargo check`, else `go build ./...`, else none. With none, the gate is skipped and the result carries a visible warning that the merged result was not built or tested. The proposal's apply is the user's approval; `refresh` (run at startup and by `finalize`) moves a `merging` campaign to `done` when its proposal was applied and back to `reviewing` when it was rejected.
- Tools `campaign_verify`, `campaign_merge`, `campaign_orphans`, coordinator only. `campaign_merge` is not blanket always-ask: merging into the integration branch does not touch the user's checkout, so only the `finalize` step asks (always, with the command shown).
- **Gaps closed.** An idle coordinator is woken by mail from the finished task through the mailbox auto-wake path (a running one still gets a step-boundary notice, and a failed send falls back to it). `awaiting_input` and `awaiting_approval` are mirrored from the pending ask and approval stores by a 10 s sweep. Per-task wall-clock, step and token limits are enforced by the same sweep: the run is aborted and the task is `failed` with the reason. The project token budget counts live runs, warns at 80 percent and stops starts at 100 percent. A task whose pane closed before its run began is detected (not shown, no run, past a 15 s grace) and re-queued through `interrupted`. `agent_campaign_orphans` and `campaign_orphans` list the worktrees finished campaigns left, with what removing each would destroy; nothing deletes them.

Defects from the final live QA (real model, merged tree), fixed:

- **D1 node tests hung in the sandbox.** Root cause: `node --test` runs each file in a child process with piped stdio; libuv builds those pipes as named pipes, the AppContainer is refused that namespace (`ERROR_ACCESS_DENIED`), and libuv retries with a new name forever, so the spawn never returned (a script's own timeout cannot fire either). A second cause hid behind it: Node's `realpath` `lstat`s every ancestor of the script and the container may not read them (`EPERM lstat 'C:\Users\<name>'`, or `C:\tmp` in the QA data folder). Fix: inside the container `NODE_OPTIONS` carries `--preserve-symlinks --preserve-symlinks-main` (a caller's own value wins); the PowerShell prologue wraps `node`/`node.exe` so `node --test` gets `--test-isolation=none` (`--experimental-test-isolation=none` on Node 22.8 to 23.5), gated on `FLINT_SANDBOX=appcontainer`, which only the container's environment builder sets; a timed-out run that looks like a test runner appends cause, remedy and the shell kind (`node_runner::timeout_note`); the bash tool description says the same. Not fixable from our side: any other Node program that spawns children with piped output inside the container (the note says so; `pnpm` projects may dislike `--preserve-symlinks`).
- **D2 BLOCKED on an empty diff, and a wedged BLOCKED.** Root cause: a retried task is started again in its existing worktree and the runner recorded the branch's current tip as the task's `baseSha`, so `base..tip` was empty. The recorded base is now kept once set (`apply_patch`), the diff base is the fork point from the integration branch (`task_base`, merge-base, falling back to the record), and the evidence is the worktree against that base: committed plus uncommitted tracked changes, and the text of new untracked files (`verify_prepare`, `task_diff`). A finished task whose verdict is BLOCKED is a first-class recoverable state: `isVerificationBlocked`, the dot `needs-you`, word `verifyBlocked`, and `recoveryOf(task, all)` returns `{state, reason, blocks, actions}` with the actions `verify` (check again, `board.verifyAgain`), `accept` ("Accept anyway": a task move to `verified` carrying `patch.accept {by, reason}`, recorded as `manualOverride {by, reason, at, previousVerdict}` and a `task-accepted-manually` event, `board.acceptAnyway`) and `skip`. The coordinator may call `campaign_verify` again but has no way to accept; its status digest carries `needs_decision` and `accepted_by`.
- **D3 PowerShell cache committed.** Root cause: inside the container `GetFolderPath(LocalApplicationData)` is empty, so PowerShell's module cache path collapsed to `Microsoft/Windows/PowerShell/ModuleAnalysisCache` relative to the working folder. `PSModuleAnalysisCachePath` now points at the sandbox scratch. As a second line, `commit_pending` (`agent_worktree_commit_pending`, new optional `declared`), the proposal builder, the verification evidence and the board diff leave out tool caches (`Microsoft/Windows/PowerShell/`, `.cache/`, `node_modules/.cache/`, `__pycache__/`, `*.pyc`, `.DS_Store`, `Thumbs.db`) unless a path the plan declared covers them (`worktree::is_unwanted_cache`; `.` never counts as a declaration). Left-out files stay on disk, untracked.
- **D4 tasks ran in ask mode.** The plan card carries one structured choice (`approval-choice`, rendered under the details by `ToolApprovalActions`): "Let tasks work on their own inside their own folder (recommended)" (default, Auto mode inside the managed worktree: edits and test commands there run without asking; anything outside it, deletes outside it, network and destructive commands still ask) or "Ask for each action". The choice is recorded with the approval: `integration.modeCeiling` (`auto` or `ask`, never `bypass`) and `limits.taskAccess` (`worktree` or `ask`), shown in the plan summary and the tool result, and `taskModeFor` reads the ceiling as before.
- **D5 same failure three times.** A Node test run that timed out is a stable failure (`test runner cannot start in the sandbox`): the loop guard stops at the second occurrence instead of the third and its notice names the shell and the remedy (`stableFailureAdvice`). The runner then records the task as `failed` with `detail` starting `needs help:` (`campaignHelp.ts`, `isNeedsHelp`) and tells the coordinator the hint to retry with. The three-strike guard for other repeated errors is unchanged.

Backend improvements (conflict resolver, editable plan, one scheduler, verification trust, estimate, campaign diff, notifications):

- **Conflict resolver.** A verified task that conflicts is parked as `conflict` as before, and then (by itself on the first conflict, or on request with `campaign_merge resolve=[ids]` / command `agent_campaign_resolve(id, taskId, sessionId)`) a resolver session starts: a fresh worktree keyed by the new session, branched from the integration branch's CURRENT tip, with the task's branch merged in `--no-commit` so the conflict markers are in the files. The task moves `conflict -> resolving -> running`; its record now points at the resolver's session, branch, worktree and base (the originals are kept in `task.resolver`). The seed (`tasks/<id>/resolve.md`, also returned in `agent_campaign_context` as `resolutions`) holds the instructions, then both sides' handoffs (the task's, and the merged tasks that declared paths covering the files, else the latest three) and the conflict regions with context, all inside an `UNTRUSTED CONFLICT DATA` fence. The resolver commits (the merge commit), the run settles `completed`, and verification and merge are the ordinary path. One attempt per conflict: `resolver.attempts` is capped at 1, so a conflict after the resolver (the integration branch moved) returns to `conflict` and `agent_campaign_resolve` refuses with a retry-cap error; a person steers, retries or skips. A resolver whose files still hold markers cannot PASS (see verification trust). A restart turns `resolving` into `interrupted` and the task continues from its stored brief. Retry of a failed resolver uses the resolver's session. Not done: restoring the original branch fields when a resolver is aborted before its pane opens (the task returns to `conflict` pointing at the resolver worktree).
- **Editable plan.** `agent_campaign_plan_update(id, {ops, title, tokenBudget})` with ops `add`, `update`, `remove`, `reorder`, `replace`. Only in `planned` or `draft`; the whole result goes through `validate_plan` and nothing is saved when it fails; `plan-updated` is logged and the estimate is recomputed. The coordinator calls `campaign_plan` again with `campaign_id` to revise a plan that is still planned (for instance one left behind by an aborted run); it replaces the tasks and goes through the same approval card. The backend record stays the truth after a person edits the plan while the card is open.
- **One scheduler.** `campaign_scheduler::next_actions` is the source of truth. The runner calls `agent_campaign_next_actions(id, live{liveTasks, freePanes, liveTokens}, maxParallel)` and uses the TS `nextActions` only when the command is missing or throws. Both are driven by `web-app/src/lib/campaignScheduler.fixtures.json` (Rust test `the_shared_fixtures_decide_the_same_way`, vitest `campaignScheduler.parity.test.ts`). The budget counts the worker's tokens (or the live run's, when larger) plus the verifier's.
- **Verification trust.** (a) The verifier's tokens are recorded on the task as `verifyTokens` (kept apart from `tokensUsed`, which a settle overwrites) and count against the budget; the renderer's figure is an estimate (about 4 characters a token, request plus reply) because the utility call returns text only; the exact counts stay in the utility-agent audit. (b) `verify_prepare` runs the detected or configured check in the task worktree and stores it as `task.evidence.check` (command, exit code, timed out, output tail). A verifier PASS with a failing check becomes FAIL (the task is repaired once, as for any FAIL), a PASS with a check that timed out becomes BLOCKED, and a verifier FAIL is never raised by a passing check. `VerifyOutcome` carries `downgraded` (why) and `check`; the event log gets `task-verdict-downgraded`. (c) A PASS whose evidence diff is empty (no diff, no new file, no pending work) while the acceptance criteria name files (a path with a separator or a `name.ext`) is BLOCKED, and a resolver's PASS with conflict markers left is FAIL.
- **Cost estimate.** Every recorded or edited plan carries `campaign.estimate` (`tasks`, per task low/expected/high, totals, `basis` `history` or `default`, `samples`): the mean tokens of finished tasks of earlier campaigns when there are at least three, else 60 000 per task (worker plus one verification), range 0.6x to 1.8x. It is in the approval card's summary and payload and in the `campaign_plan` and `campaign_status` results. Retries are not included.
- **Campaign diff.** `agent_campaign_diff(id, patches?)` returns the integration branch against the campaign's base commit in the `TaskDiff` shape (files, status, counts, capped patches, totals, truncated), re-deriving the integration worktree from Git first.
- **Desktop notifications.** The runner shows one notification (the app's `notifyInBackground`: only when the person granted notification permission and the window is not in front) when a campaign needs the person (a task awaiting input or approval, failed, conflict after the resolver, verification blocked), reaches `reviewing`, `done` or `failed`. Each is claimed first with `agent_campaign_claim_notice(id, key)`, which appends `desktop-notified` to the event log, so a transition notifies once and a restart does not repeat it. There is no separate app setting for it; the browser permission is the switch.

Known gaps and limits:

- The fixes above are covered by unit tests and need one more live pass. Verification, merge and gate were exercised by Rust fixture-repo tests (clean merge, conflict, topological order, dependents unblocked, path and branch and base re-verification, gate selection, gate fail and pass, proposal creation without writing the checkout) and by vitest with mocked invoke; not smoke-tested in the running app.
- A step is counted as one tool call in the live run's turns, not the Rust loop's step index.
- No `add_task` to a running plan (an approved plan's tasks are fixed).
- The verifier's tokens on the task are an estimate from sizes (see verification trust); `runUtilityAgent` would need an `onUsage` callback for exact counts.
- The campaign-wide diff and the plan edit have no UI of their own yet; the commands and the `Campaign` fields (`estimate`, task `evidence`, `resolver`, `verifyTokens`) are what a screen reads.
- A campaign with a failed or conflicted task finishes only after the coordinator skips it (`campaign_merge skip`); `campaign_cancel` cancels everything.
- Gate and task checks run the repository's own commands with the user's shell, bounded by a deadline (180 s for a task check, 600 s for the gate). A repository can set the gate command in its `agent.toml`; the finalize approval shows it first, but the per-task check that runs while verifying uses the detected or configured command without a prompt.
- Pane-bound parallelism, the 12-worktree disk cost and pause and resume remain P7.
- A notice reaches a running coordinator at its next step boundary and is in memory only; the event log re-pushes after a restart.
- The integration worktree (`campaign-<id>` key) and task worktrees are kept until the user discards them.
- Added locale keys are English in every locale file.
- Board: the files-changed counts come from git (`agent_campaign_task_diff`); a task whose worktree was removed shows the recorded file names only. Last activity comes from the renderer's session store, so it is blank for a session that was deleted. The new board, start dialog and changes panel are covered by vitest (mapping, grouping, headline, diff formatting, start flow, render) and by Rust fixture-repo tests for the diff; they were not smoke-tested in the running app.

## Using campaigns

1. Open the Cowork tab of the sidebar. **Campaigns** (beside Rooms) opens the overview of your campaigns, with a "Start a campaign" button; the same action is in the menu of the New session row. The row is always there; the start action says "Open a git folder to start a campaign" when the folder is known not to be a git repository.
2. Describe the big task in the box and press Start. Flint opens a coordinator session, looks at the repository and proposes a plan of up to 12 tasks. Nothing starts until you approve the plan.
3. Approved tasks run in parallel (as many as Settings, Agent tools, "Campaign parallel threads" allows), each in its own worktree. The coordinator and all of its tasks stay together in one sidebar group, each row with one status dot; click the group's title to open the board.
4. The board tells the story. Each task has a sentence of what happened ("Wrote 4 files, +176 -0 lines"), how long it took and a "What happened" fold with what it was asked, the files read and written and the commands run, in order. A task that is stuck shows the real error, one recommended action, and Retry with an optional "Tell it what to do differently" box whose text leads the retried task's first turn. Skip and Open conversation sit beside it. Branch, attempts and token counts stay under each task's Details.
5. Under the tasks the summary gives the goal, a map of what ran side by side and what waited, the time taken, one cost figure and the branch the results are collected on, with a copy button.
6. When every task is done the board says "Ready for your review" with a wrap-up of what got built. Review changes runs the final build and test check and creates one proposal for your checkout; applying it is your decision.

7. Before you approve, the plan card shows a rough cost ("About 40k to 90k tokens", and what it depends on) and the tasks as a short list. **Edit plan** opens an editor: rename a task, change what it does, how we know it is done, which files it may change and what it waits for, add, remove or reorder tasks. Problems (an empty description, a loop of waiting tasks, two parallel tasks changing the same files, more than 12 tasks) are named under the editor, and **Save changes** is needed before you can allow the plan.
8. A task that clashes with another one shows the files in conflict, a plain explanation and three choices: **Try to resolve automatically** (a resolver session merges it, progress shows on the row), **Open conversation** and **Skip task**. A finished task's Details show the verifier's verdict, whether its tests passed (with the end of the output when they failed) and the tokens spent on checking.
9. **Review changes** in the wrap-up opens everything the campaign changed, file by file with expandable diffs (a file two tasks touched is listed once); the final build and the proposal you apply are unchanged. A split tab shows a check mark only for a task that verified or merged (or a Cowork run that ended normally) and a red mark for one that failed.

You can also just ask for a campaign in a Cowork chat on a git folder ("split this into parallel tasks and plan it as a campaign"); the model has the same `campaign_plan` tool.

From your phone: the phone app (see `docs/MOBILE.md`) has **Campaigns** under Cowork in its menu. It lists your campaigns with the same one-line headline, then shows one campaign with its progress, the tasks grouped Needs you, Working, Up next and Done, how many files each task changed, and the approval cards of the coordinator and its tasks (the plan card included). Pause, Resume, Cancel, Retry, Skip and Stop are there, and when the campaign is ready, Check and prepare changes runs the same final check, then Apply lists the files and applies them to your folder. Files with a review flag need a tick first, and sensitive files are never applied. All of it goes through the computer's own campaign commands and works only while Approvals from phones is on. The phone cannot start a campaign; start it on the computer or ask for it in a Cowork chat from the phone.

## Open questions

1. Decided: the UI name is Campaigns. Legacy "project" (folder) naming is untouched.
2. Decided: parallelism stays pane-bound for the MVP, default 4, user-configurable 1 to 6 in settings. Removing the pane cap needs the run driver extracted or the headless CLI worker (P7, optional).
3. The scheduler lives in the renderer, so closing the window pauses everything. Backend state keeps resume correct.
4. Mailbox rate limits could throttle heavy steering; a campaign-origin exemption would be a security-sensitive change in `session_mailbox.rs`.
5. Coordinator notices must not count as depth-greater-than-zero replies or they will be blocked by the loop guard (`lastRunWasWake`).
6. Textually clean merges can still break the build; the final build and test gate is the only defense, and its command source (agent.toml or detected) is undecided.
7. Worktree disk use and Windows path length with up to 12 worktrees; may need `agent_worktree_optimize`.
8. Cost: N parallel top-level sessions multiply spend. The plan card needs an estimate and a sane default budget.
9. Uncommitted work in the source checkout is invisible to worktrees (existing behavior); the plan card must say so.
10. Adding the `campaign` field to persisted sessions needs a migration bump in `useCoworkSessions.ts`.
11. Backend and renderer state can disagree after a crash. Rule: the backend wins for status, the session store wins for transcript.
12. Decided in P4: the renderer runs the model call; the backend builds the fenced request and parses the verdict (`agent_campaign_verify_prepare` and `_verify_finish`).

## A server-driven campaign

A campaign record has an additive `driver`: `renderer` (the default, and what every earlier record means) or `server`. A `server` campaign is run by `flint serve --agent-run` with no client connected: a driver task on the server starts tasks with `next_actions`, runs each in a runner session on its own worktree, settles it, verifies it with the server's model, merges in topological order, starts one resolver on a conflict, honours the limits, and continues by itself after a restart. The plan comes from a one-shot planner model call (strict JSON, held to `validate_plan`), not from a coordinator session, and it waits for a person's approval (`agent_campaign_approve`); the final gate and the proposal wait for another (`agent_campaign_finalize`, then the ordinary proposal apply). The desktop's campaign host, runner kick, sweep, resume and verify do nothing for a server campaign, and a campaign made on the desktop is never driven by a server. The design, the commands, the security notes and the gaps are in `docs/MOBILE.md`, "What P3 does".

Known differences from the desktop: no coordinator conversation (no `campaign_steer`, `campaign_decide` or `campaign_collect`), no task moves from a client (retry, skip, accept anyway, verify again), and parallelism is bounded by `--agent-max-sessions` instead of panes. Not verified here: a real provider, a real build command under `--agent-allow-checks`, a resolver end to end on the server, the sandbox under a task, and the board against a server in a real browser or the Android WebView.

## On the Android build and a headless server

Campaigns do not run on the .apk itself. What a headless server can do, with `flint serve --agent-root <folder>`: list campaigns, read their decisions, handoffs and event log, pause, resume and cancel them, and review, apply or reject proposals. With `--agent-run` as well it runs campaigns itself (the section above): the .apk (or any browser at the server) plans one, approves it, watches it and applies the result, and the server does the work. Without `--agent-run` it cannot start a campaign, run a task, verify, merge or run the final gate, and a client cannot move a task or approve a plan through the review plane. Setup, the command table and what blocks a server-side runner are in `docs/MOBILE.md` ("Using the .apk with a headless Flint server"). A server-side runner is the open item P7 names; its design, phases and security model (the Rust loop on the server, `--agent-run`) are in `docs/MOBILE.md` ("The server runner"), and P0 of it (probe and read-only session views) is in.
